# راهنمای کامل تست آپارتمانت

> آخرین به‌روزرسانی: ۱۴۰۵/۰۸/۰۷ (۲۰۲۶-۱۰-۲۹)، نسخهٔ ۱.۸.۰
> قبل از هر انتشار، دست‌کم مرحلهٔ ۱ و ۲ اجرا شود. برای تغییرات بزرگ همهٔ مراحل اجرا شود.

## مرحلهٔ ۱: تست‌های خودکار (روزمره)

| دستور | چه چیزی را تست می‌کند | زمان تقریبی |
|---|---|---|
| `npm test` | همهٔ تست‌های واحد (۹۰۸ تست): محاسبهٔ قبض، پرداخت، بدهی، گزارش، تم‌ها، پشتیبان، امنیت، چندساختمان، جلسه | ۱ دقیقه |
| `npm run build` | سالم بودن TypeScript و بیلد وب | ۳۰ ثانیه |
| `npm run test:full` | یک‌جا: تست واحد + بیلد + تست بار و سناریو با ۱٬۰۰۰ قبض | ۱ تا ۲ دقیقه |

## مرحلهٔ ۲: تست بار و سناریو (قبل از انتشار)

| دستور | چه چیزی را تست می‌کند |
|---|---|
| `npm run test:stress` | سرعت با ۱۰۰ واحد و هزاران قبض: شروع برنامه، ذخیره، علامت پرداخت، گزارش |
| `npm run test:scenario` | سناریوی چندساختمانی: چند ساختمان با چند واحد، صندوق، دوره‌های مدیریت، جلسه‌ها، بعد پشتیبان‌گیری و بازیابی و مقایسهٔ کامل داده‌ها |
| `npm run test:full -- --full` | همه‌چیز با ۱٬۰۰۰، ۵٬۰۰۰ و ۱۰٬۰۰۰ قبض (حدود ۴ دقیقه) |
| `node perf/browser-sqlite.mjs` | اندازه‌گیری داخل مرورگر واقعی (Chrome headless) |

جزئیات و اعداد مرجع در `perf/README.md` است.

### اعداد مرجع (روی کامپیوتر، نه گوشی)

| تعداد قبض (۱۰۰ واحد) | ذخیرهٔ یک قبض | شروع برنامه |
|---|---|---|
| ۱٬۰۰۰ | ~۷ ms | سریع |
| ۵٬۰۰۰ | ~۸ ms | — |
| ۱۰٬۰۰۰ | ~۱۱ ms | ~۴ ثانیه؛ بازیابی پشتیبان ~۱۵ ثانیه |

اگر عددی چند برابر این‌ها شد، یعنی کندی تازه‌ای وارد کد شده است.

## مرحلهٔ ۳: امنیت و پشتیبان

این‌ها جزو `npm test` هستند ولی وقتی پشتیبان یا ذخیره‌سازی تغییر کرد، جدا بررسی شوند:

- `tests/security.test.ts`: ورودی‌های خطرناک (`__proto__`، `constructor`)، سقف طول متن، فایل‌های پشتیبان دستکاری‌شده.
- `tests/fullBackup.test.ts`: پشتیبان v9 همهٔ ساختمان‌ها، صندوق، دوره‌ها، جلسه‌ها و ساختمان فعال را دارد؛ بازیابی اتمیک است (خطا ⇒ برگشت کامل)؛ نسخهٔ احتیاطی قبل از بازیابی.
- **تست پوشش:** اگر جدول یا تنظیم تازه‌ای اضافه شود و در پشتیبان نباشد، این تست خطا می‌دهد. یعنی هر قابلیت جدید باید به پشتیبان هم اضافه شود.
- پشتیبان‌های قدیمی v1 تا v8 باید هنوز بازیابی شوند (فایل‌های نمونه در `tests/fixtures`).
- `tests/persistence.test.ts` و `persistNative.test.ts`: ذخیرهٔ ژورنالی، اسنپ‌شات تکه‌ای، سالم ماندن فایل اگر برنامه وسط ذخیره بسته شود.

## مرحلهٔ ۴: تست دستی روی گوشی واقعی

هنوز انجام نشده و قبل از انتشار عمومی لازم است:

- [ ] نصب APK روی یک گوشی ضعیف و یک گوشی متوسط.
- [ ] ساخت ۲ یا ۳ ساختمان، هرکدام با چند واحد؛ صدور قبض، ثبت پرداخت، صندوق، جلسه.
- [ ] پشتیبان‌گیری، پاک کردن برنامه، نصب دوباره و بازیابی؛ همهٔ داده‌ها باید برگردند.
- [ ] بستن ناگهانی برنامه وسط ذخیره و باز کردن دوباره؛ داده نباید خراب شود.
- [ ] داده‌های زیاد (چند هزار قبض): زمان باز شدن و بازیابی روی گوشی یادداشت شود.
- [ ] نصب نسخهٔ جدید روی نسخهٔ قبلی (بدون پاک کردن)؛ داده‌های قبلی سالم بمانند.

## مرحلهٔ ۵: رابط کاربری و تم‌ها

برای هر تغییر UI، چک‌لیست `docs/TESTING-CHECKLIST-fa.md` اجرا شود (همهٔ ۹ تم روشن و تاریک، تیک‌ها، کشوها، آموزش).

## ساخت APK بعد از پاس شدن تست‌ها

```
npm run build
npx cap sync android
cd android && ./gradlew assembleDebug
```

(روی ویندوز: `scripts/build-apk.bat`)

## کارهای باقی‌مانده (پیشنهادهای امنیتی، نیازمند تأیید)

- `allowBackup="true"` در اندروید.
- نبود CSP.
- رمزنگاری نشدن فایل پشتیبان.
- گزارش‌های خیلی بزرگ بدون مجازی‌سازی لیست.
- `minifyEnabled false` در نسخهٔ release.
- بارگذاری کامل داده در شروع برنامه روی رشتهٔ اصلی.
